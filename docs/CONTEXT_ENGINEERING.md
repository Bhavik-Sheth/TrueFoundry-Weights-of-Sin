# Context engineering for repository edits

The model needs a working set for the next decision. For a CLI behavior change, that can mean the option declaration, the handler, its shared defaults, a test that states the contract, and the relevant help text. A broader file map lets the model find nearby code without spending its edit budget on every match. As the task progresses, the working set changes from discovery to exact source, then to the reviewed diff and verification results.

## How the working set changes during a task

| When | What reaches the model | What Contexo keeps available |
| --- | --- | --- |
| Start | The user goal, selected source when supplied, a ranked file map, and source excerpts with paths, lines and selection reasons. | Index symbols, call and import evidence where available, file key terms, live search, and Git history. |
| Locate the change | Exact implementation, test and documentation pointers. A candidate range suggests where to read next. | Bounded source ranking protects these roles through the serialized tool-response budget. The delivery receipt records sent, shortened and omitted excerpts. |
| Establish current behavior | A bounded read with current text, inclusive line coordinates, full-file revision hash and eligibility for a range edit. A history request can return short diffs, the latest commit's stated rationale, and exact historical lines. | Live editor text or working-tree text, Git HEAD, and the prior committed version. Each view has different authority. The current buffer or checkout is the base for a write. |
| Propose and review | For a range edit, the model sends the path, exact coordinates, base hash and replacement text. Its response budget goes toward the change. | The harness constructs the full diff from the current source and checks bounds, revision and overlap. The editor displays affected files and saves accepted hunks. |
| Recover after context pressure | A bounded run checkpoint restores the original goal, selection/source pointers, proposal decisions and recorded checks. The agent opens current lines again before proposing another patch. | The run journal retains the exact delivered packet fingerprint and paged review records. TrueForge owns its transcript compaction. Copilot and Claude Code own theirs. |
| Verify | The agent gets bounded check results and links them to the change it proposed. | The journal and native review preserve the evidence behind observable actions. A short explanation can cite a source or test. |

A 32,000-token retrieval request can still yield a much smaller tool packet. The source-token target and the 22,000-character serialized limit govern different budgets. The former controls candidate packing. The latter controls what actually crosses the MCP boundary after escaping. The live HTTPX comparison confirmed that keywords passed as bare mentions stay soft, so a generic identifier cannot reserve source ahead of the actual CLI. The provider's real input count also includes its prompt, tool definitions, conversation, reasoning state where applicable, and previous results. Reserve output space before choosing how much source to send.

## Caching and freshness

Contexo reuses the lexical indexes, path postings and recent ranked lists attached to the same immutable symbol snapshot. A changed snapshot rebuilds them. Live search and current source reads run against the workspace for each request. Sparse TF-IDF vectors score indexed documents that share a term with the expanded query. These vectors come from the local corpus. Immutable Git blobs and history are reused by repository, revision and path. The file map still reads current text and resolves HEAD for each request.

A provider prefix or KV cache saves model-side work when the provider can reuse that input. A local retrieval hit saves repository-side work. Measure the former using provider counters and first-token latency, and the latter using retrieval latency and hit rate. The source revision hash still governs whether a proposed edit can proceed.

## Limitations and release checks

The harness refreshes context at requests and tool boundaries. It has no portable API for changing the evidence seen by a model during active decoding. Provider steering, model memory and transport compaction require runtime support. Provider KV savings have not been measured in this integration.

A runtime-integrated version can rebuild the next model input after a tool result, a review decision, or a user scope change. The persistent record should hold the explicit goal, constraints, dependency-ordered batches, expected checks, current review decisions and source revisions. For a bounded next step, pin that task state first. Load exact code for the active files and their closest dependencies. Page older tool output only when a decision calls for it. On a workspace revision change, invalidate the affected source and keep the earlier review decision attached to the revision it covered. At the runtime's context threshold, compact the narrative history and preserve the structured record. Test that the next provider request receives it even when the prior transcript has been summarized.

The next test should compare one-shot, iterative exact-read, and forced-compaction runs on the same pinned tasks. Use the complete judged patch and independent tests as the outcome. Record coverage of required file roles in the actual delivered response, wasted evidence, tool calls, stale-read retries, prompt and completion tokens, first-token latency and cache counters. For a 100-file task, force compaction between dependency-ordered batches and verify the task constraints, prior decisions and check status after each restore. The current 120-file checkpoint test exercises pagination, and the upstream retrieval probes exercise source selection. End-to-end Bonsai tool dispatch and reviewed multi-file completion remain separate release checks.
